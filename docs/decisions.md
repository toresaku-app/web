# 1. プロダクト・技術

## 疾患タグ（conditions）は不採用 ★再提案厳禁

- **検討時**: Phase 8 の型拡張で `conditions?: string[]`（膝 OA、腰痛、脳卒中等）を追加予定だった
- **却下理由**: SaMD リスク。「膝 OA → この運動」と紐づけると、アプリが疾患に対して運動を推奨していると解釈される
- **代替**: 部位・姿勢・カテゴリの 3 軸フィルタで絞り込む。運動の選択は PT の臨床判断に委ねる

## Category 型から「体幹」を削除

- **発端**: 「種類のところに体幹って入ってるのはなぜ？」という指摘
- **理由**: 「体幹」は部位フィルタ（下肢/体幹/上肢）にも存在し、重複して紛らわしい
- **対応**: 体幹カテゴリの運動 4 種（ドローイン、ダイアゴナル、プランク、トランクローテーション）を「筋トレ」に統一
- **現在の Category**: `"筋トレ" | "ストレッチ" | "バランス" | "ADL" | "呼吸"`
- **教訓**: 体幹は `bodyPart` であって `category` ではない

## 並べ替えはドラッグではなく上下ボタン方式

- **調査結果**: react-native-draggable-flatlist は Web 対応が不安定、@dnd-kit は RN 非対応、PanResponder 自前実装は ScrollView とのジェスチャー競合が複雑
- **採用**: 上下ボタン（▲▼）方式。先頭/末尾では該当ボタンを `opacity-20` で無効化

## フィードバック収集は Google Forms

- **却下**: mailto — メール管理が煩雑、Web 版でメーラー未設定だと送れない
- **採用理由**: 回答がスプレッドシートに自動蓄積、メール設定不要、無料
- **フォーム項目**: カテゴリ（必須: 新しい運動の提案 / 機能リクエスト / バグ報告 / その他）、内容（必須）、ご職種（任意）
- **UI 配置**: ヘッダー右上（「ご意見」）+ フッター（「ご意見・ご要望」）の 2 箇所

## 休息時間パラメータ

- デフォルト 10 秒、5 秒刻みで増減
- 0 秒にすると PDF に非表示（条件: `sel.restSeconds > 0`）
- `SelectedExercise` に `restSeconds: number` として追加（optional ではなく required）

## 注意事項・禁忌システムは保留

- Phase 6 に「疾患選択で警告表示」の TODO があるが、SaMD リスクとの境界が曖昧
- 「この疾患にはこの運動をしないでください」は治療判断に近い
- 実装するなら要再検討

# 3. インフラ・開発フロー

## develop/main ブランチ分離 + Vercel ステージング

- GitHub Pages 単体ではステージングが困難なため、Vercel + GitHub Pages を併用
- main ブランチ保護: `required_pull_request_reviews`（approving_count: 0）+ `enforce_admins: true` + `allow_force_pushes: false`
- `vercel.json`: baseUrl `/web` の問題を解消するため `/web/*` → ルートへのリライトを設定

## PR は承認を得てからマージする ★最重要

- 過去に確認前にマージして問題になった経緯あり
- PR 作成後は「プレビューで確認してください」で止める。明示的な承認を得てからマージする

## リポジトリは public のまま（当面）

- バックエンドなし・API キーなしで漏洩リスクが低い
- GitHub Pages 無料プランは public 必須
- **将来**: カスタムドメイン取得 → Cloudflare Pages or Vercel に移行 → private 化

## LP は `public/lp.html` に配置

- **経緯**: 当初は GitHub Actions 内の heredoc で生成していたが、Vercel プレビューで表示されない問題が発生（Expo ビルドに含まれないため）
- **解決**: `public/lp.html` に移動（Expo が自動で dist/ にコピー）+ `vercel.json` に `/web/lp.html` → `/lp.html` のリライト追加

## SEO

- 構造化データに Organization・BreadcrumbList を追加（リッチリザルト対応）
- Search Console の「サイトマップを取得できませんでした」は放置。`sitemap.xml` は実際にアクセス可能で、Google 側の反映待ちの既知問題

# 4. 運動データ・イラスト生成

## 画像生成モデルは gpt-image-1.5 / high

- **テスト経緯**: gpt-image-1（low）→「AI で作った感が強すぎる」と却下 → medium もいまひとつ → スタイル強化プロンプト + gpt-image-1 で改善するも不十分 → gpt-image-1.5（medium）で良化 → **high を採用**
- **却下**: gpt-image-2（組織認証が必要でアクセス不可）、gpt-image-1-mini（品質不足）

## プロンプトは元の `PROMPT_TEMPLATE.md` スタイル

```
- セミリアリスティックなフラットイラスト
- 白背景、影なし
- 人物: 中年男性、短髪黒髪、白い半袖Tシャツ、紺のハーフパンツ、白い靴下
- 輪郭線: 細い黒線
- 色数: 最小限（肌色、白、紺、青）
```

- **却下**: 強化版スタイル（「完全にフラット、グラデ禁止、影禁止、立体感禁止」）
  - gpt-image-1 では強化版が良かったが、gpt-image-1.5 では元プロンプトの方が既存イラストとの統一感が高い
- **教訓**: モデルが変わるとプロンプトの効き方も変わる

## 画像生成の運用は API → ChatGPT 手動生成に移行

- **フェーズ 1**: `scripts/generate-illustrations.py` で一括生成。$5 チャージで約 24 枚生成してクレジット切れ
- **フェーズ 2**: Excel プロンプトシートを作り、ChatGPT で 1 枚ずつ手動生成 → リネーム・WebP 変換・データ登録
- **却下**: ChatGPT/Claude のサブスク内で自動化（サブスクに API アクセスは含まれない）、ブラウザ自動化（利用規約違反）

## PNG は `originals/` に退避、アプリは WebP のみ使用

- PNG（9.7MB）→ WebP（1.1MB）のサイズ差
- `assets/illustrations/originals/` は `.gitignore` 済み

## イラストは `illustrations.ts` のマッピングで管理

- `Exercise` 型の `illustration` フィールドは型に存在するが使っていない
- 運動 ID をキーに WebP を `require` する方式

# 5. 事業・マネタイズ

## 個人事業主から始める（法人化しない）

- 初期費用ゼロ。収益ゼロの段階で法人住民税（年 7 万円）や税理士費用（年 15〜30 万円）を払う意味がない
- **却下**: いきなり合同会社を設立
- **法人化のトリガー**: 利益が年 800〜1,000 万円超、B2B で法人格を求められた時、人を雇う時

## 副業としてスタート

- 本業（PT）の収入を維持してリスクを最小化。副業規定は確認済みで OK（2026-05-02）
- **独立のトリガー**: アプリの売上が本業の 50〜70% を超えたら検討
- **却下**: いきなり退職して専業

## 個人 PT/OT/ST には課金しない（無料 + 広告）★再提案厳禁

- 現場感覚として「PT が個人で課金することはない」
- 当初フリーミアム（個人月 500〜1,000 円）を提案したが明確に否定された
- **教訓**: 現場を知らない理論より、毎日現場にいる当事者の肌感覚が正しい

## 広告を入れても OK

- 「患者の前でアプリを使うことは稀。作って印刷して患者に渡すフロー」のため、患者が見るのは紙だけ
- 当初「医療系アプリに広告は信頼感が下がる」と懸念したが、利用フローを踏まえて撤回

## 収益の本命は B2B（施設プラン）、月 2,000〜3,000 円

- モデル: 個人 PT が無料で使う → 施設全体で使いたくなる → 施設契約（Slack/Notion 型の拡散）
- 施設プランの付加価値: 複数スタッフ利用、テンプレート共有、施設ロゴ入り出力、データバックアップ、利用統計、広告非表示
- 直接競合 RiGAKUサポが月約 2,000 円（Web 上では非公開の情報）
- **却下**: 当初提案の月 5,000〜10,000 円
- 最終価格は PMF 検証のアンケート結果を見てから決定

## マネタイズは PMF 検証後に開始

- **却下**: PMF 検証中に広告を入れる → フィードバックが広告への不満に引っ張られ、本質的な評価が取れない

## シンプルさを最大の差別化にする

- 競合（リハサク: 700 種動画 + チャット + トラッキング、Rehab Cloud: 加算算定 + LIFE 対応）は多機能路線
- トレさくは「紙カードをサクッと作って印刷して渡す」に特化。デジタル不慣れな高齢患者にそのまま渡せるのが強み
- **却下**: 動画配信、チャット、リアルタイムトラッキング等の追加

## 価格の透明性を差別化にする

- 競合はほぼ全社が料金非公開（「要問い合わせ」）。明朗会計にすること自体が導入障壁を下げる

## ローカルオンリー設計と SaMD 非該当の維持

- 健康情報は個人情報保護法上の「要配慮個人情報」。サーバーに保存しない設計が最強の防御
- SaMD に該当すると製造販売業許可・認証が必要（数百万〜数千万円 + 年単位）
- **絶対 NG の機能**: 「あなたの症状にはこの運動がおすすめ」「痛みの程度から回復度を評価」「AI が最適なリハビリプランを処方」
- **安全な機能**: PT が自分の判断で運動を選び、カードにする（＝ツール）

# 7. PMF 検証・院内広報

## 院内 80 名の PT/OT/ST をテストユーザーにする

- 身近に大量のターゲットユーザーがいる環境。外部でユーザーを探す必要がない

## PMF 判定は Sean Ellis テスト

- 質問「このアプリが明日使えなくなったら、どう感じますか？」で「非常に困る」が 40% 以上なら PMF 達成

## 院内広報はスライド発表ではなく勉強会形式

- 構成: 「自主トレの必要性 → 課題 → 解決策としてのアプリ」（Problem → Solution → CTA）
- タイトル: 「自主トレが変える、患者の 14 時間」全 10 枚
- シフト制のため 2 回実施（2026-05-18 / 05-22、いずれも実施済み）
- 順序も変更: 旧 Week 1〜4 の段階配信 → リマインド → 勉強会 2 回 → アンケート
  （勉強会を先にやることでアンケート回答の質が上がる）

## アンケートは 3 種に分離

| 種別 | 実施 | 内容 | 用途 |
|------|------|------|------|
| **A** | 勉強会**冒頭** | 現状の作成方法・課題感 5 項目（Likert 5 段階）・事前期待（3 問） | 学会抄録 |
| **B** | 勉強会終盤 | 完成可否・A の 5 項目に対応した評価・今後の利用意向・自由記述（8 問） | 学会抄録 + PMF |
| **C** | 2026-06-05 以降 | Sean Ellis テスト等（6 問） | PMF 判定のみ |

- **A は勉強会冒頭で取る**: 説明後だと「課題感」に説明バイアスが入る。「課題 → 解決」のビフォーアフター構造に必須
- **A の 5 項目と B の設問を対応させる**: ① 作成時間 ② 運動の選択肢 ③ イラスト・図解の質 ④ カスタマイズの手間 ⑤ 患者が理解・継続しやすい指導書になっている自信
- **A の Q3 は「事前期待」設問**: 「現時点で、自主トレ指導書作成アプリに興味はありますか？」（説明前でも答えられる形に修正）
- **C の Sean Ellis 設問には「すでに使っていない」を含める**: 脱落者を捕捉するため。3 択に統合する案は却下
- **C の配信は 6 月以降**: 継続使用後の評価を取るため、勉強会から 2 週間以上の使用期間を確保

## 回収方法は QR コード + 当日の強制回答時間

- 勉強会の最後 3 分を「QR を読み取って回答してから退室」タイムにする（質疑応答の前に配置）
- メアド収集は OFF（個人情報最小化 + 心理的抵抗を下げる）
- 回答後の画面に LP リンクを置いて、回答 → DL の導線にする
- **却下**: 紙メインで回収して後日代入力する案 —「入力作業が手間すぎる」
  - **教訓**: 手作業の代入力・代転記を含む段取りは、規模が小さく見えても受け入れられにくい

## ハンズオンの想定患者は各自の担当患者で自由設定

- 全員に同じ患者像を指定する案は却下。学会データの均質性より現場のリアルな評価を優先

# 8. 学会発表（リハビリテーション・ケア合同研究大会 高知 2026）

> 進行状況・スケジュールは [tasks/conference-2026-kochi.md](../tasks/conference-2026-kochi.md)、

## 発表形式はポスターを選択

- 理由: 気になった人がいつでも見に行けるから
- 動機: 認知拡大 + 実績づくり

## 演題名は「自主トレ指導書作成アプリ『トレさく』の開発と使用感の予備的評価」

- 30 字（規定は全角 60 字以内）、一文型・副題なし
- 「予備的評価」で学術的謙虚さを保ちつつ「評価」という結論示唆ワードを残す
- 学会発表は宣伝目的も兼ねるため、アプリ名を演題名に明示する方針
- **却下**: 「院内パイロット評価」（カタカナで伝わりにくい）、「PT/OT/ST 21 名による評価」（本文と重複）、副題型
- **注意**: 「予備的」と書いた以上、考察で限界（多施設・大規模調査の必要性）を明示する一貫性が必要

## 切り口は「課題解決型」→「アプリ開発 + 予備的評価型」に転換（2026-05-27）

- 当初は「自主トレ指導書作成の課題と解決策の検討」だった
- **却下**: 純粋な「開発報告」として出す案 → 結果がないと不採択リスクが高い

## N の分母は「院内 80 名」ではなく「勉強会参加者 21 名」

- 80 名には夜勤・休職・他病棟で勉強会に来られない人が含まれ、母数として不適切
- **正しい見せ方**: 勉強会参加者 21 名のうち回答 21 名（回答率 100%）
- **却下**: 「80 名中 21 名（回収率 26.3%）」「職種別内訳」（職種設問を収集していないため記載不可）
- 回答率 100% は「強制回答時間を設けた運営設計の成果」として書く（任意性への疑問を招かないため）
- **教訓**: N の見せ方を提案する前に、(1) アンケートで何を収集しているか (2) 母数の定義として何が正確か、を必ず確認する

## 抄録に入れる数値の優先順位

1. **回答率 100%**（21/21）— 強制回答時間の運営設計を一言添える
2. **B Q2 ①「作成時間短縮」平均 4.76**（全員 4+5）— 最強の数字、必ず入れる
3. **B Q1 完成率 81%**（17/21）— 10 分のハンズオンで 8 割完成
4. **A Q2 最大課題「イラスト・図解」90.5%**（4+5 合計）— 課題側のトップを 1 つだけ
5. **A の現状作成方法トップ「Office 系 52.4%」** — 現状の輪郭を 1 数字で
6. **B Q3 ポジティブ 100%** — 事後評価の総括
7. A Q3 → B Q3 の中立 1 名 → ポジティブ移動（余裕があれば）

## 大会規定（2026-05-26 確認）

- 抄録本文: 全角 600 字以内 / 演題名: 全角 60 字以内
- 発表形式: デジタルポスター（PDF をフルハイビジョンモニターに投影）
- COI: 必須（スライド 2 枚目に開示、提出日基準で過去 1 年）。**抄録本文への記載は不要**
- 演者数: 最大 15 名 / 所属最大 5 施設。主催 7 団体いずれかの会員資格が必要
- 構成指定なし（ただし「背景→目的→方法→結果→考察」が標準）
- **600 字の配分**: 背景・目的 100〜120 / 方法 120〜150 / 結果 200〜250 / 考察・結語 100〜130。個別 5 項目の数値はポスター本体の表に逃がす

## 同一筆頭演者で 2 演題体制（事務局承認済み）

- 領域・切り口・データソース・聴衆ターゲットが分離しており重複リスクは低い
- 2026-05-28 に事務局（実行委員長）より 2 演題可・時間配慮 OK の回答を受領
- 2026-07-24 に同一セッション内の進行も確認済み

## 引用文献の調査結果（2026-05-17）

抄録は A+B のデータを主軸に再構成する方針となり新規引用は保留したが、勉強会スライドで使った文献の調査結果は以下の通り。

**① Kanai et al. (2023) JAPA — 著者取り違えが判明**
- スライドの「Ohtsubo et al.」表記は誤り。正しくは **Kanai, Nozoe, Ohtsubo, Yasumoto, Ueno**（Ohtsubo は第 3 著者）
- *Relationship of functional outcome with sarcopenia and objectively measured physical activity in patients with stroke undergoing rehabilitation*, Journal of Aging and Physical Activity, 2023, Vol.31(1)
- 主要アウトカムは **FIM-M（運動項目）**。引用時は「退院時 FIM-M」と明記する
- 対象: 脳卒中患者 N=80、中央年齢 72.0 歳

**② Tyson et al. (2015) NNR — 介入設定の読み替えが必要**
- Neurorehabil Neural Repair. 2015 Oct;29(9):818-26. DOI: 10.1177/1545968314565513
- 「5〜15 分/日 × 7 日以内」は Abstract に明記あり。「30 分/日 × 28 日」は Abstract に記載なし（本文 Methods 要確認）
- **在宅自主トレ HEP ではなく入院中の患者主導療法 RCT**（上肢ミラーセラピー + 下肢エクササイズ）。引用するなら「入院中の患者主導療法における推奨と実態のギャップ」として記述する
