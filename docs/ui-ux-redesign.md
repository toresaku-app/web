## 1. 出発点 — 現場の課題（アンケートAの実測、N=21）

| # | 課題 | 現行アプリの応答 | 評価（B調査） |
|---|------|----------------|--------------|
| ① | 作成時間がかかる | 選ぶ→調整→PDF の3ステップ | **平均4.76**（最強の数字） |
| ② | 運動の選択肢が乏しい | 100種ライブラリ | 応えている |
| ③ | イラスト・図解の質 | 統一スタイルのイラスト100枚 | 課題側の最大値90.5%に応えている |
| ④ | カスタマイズの手間 | 回数/セット/保持/休息/頻度/メモ | 応えている |
| ⑤ | **患者が理解・継続できる指導書になっている自信** | **明示的な支援なし** | **ギャップ** |

結論: ①〜④は「作る」支援として成立済み。⑤は「渡した後」の支援であり、現行アプリはフローの途中で支援を終えている。

## 2. 臨床フローと支援マップ

理学療法士が自主トレを提供する実際のフロー（回復期・外来・訪問共通の骨格）:

```
[1]評価・処方判断 → [2]運動選定 → [3]用量設定 → [4]個別化 → [5]確認・出力
                                                                    ↓
[9]再評価・調整 ← [8]自宅での実施(患者) ← [7]手渡し・共有 ← [6]説明・実技指導
      └──────────────── 次回、[2]に戻って微調整 ─────────────────┘
```

| フェーズ | 行為者 | 現状の支援 | ギャップ | 施策（→§4） |
|---|---|---|---|---|
| 1. 評価・処方判断 | PT | **なし（意図的）** | なし。SaMD非該当維持のため踏み込まない | 対象外と明文化 |
| 2. 運動選定 | PT | 検索 + 3軸フィルタ + サムネイル | フィルタが画面を占有しリスト初期3件のみ／「四つ這い」「呼吸」が視界外／選択前に運動の詳細（説明・ポイント）を確認できない／選択済みを見返せない | A-1, A-2, A-3 |
| 3. 用量設定 | PT | ステッパー + 臨床的デフォルト値 | ボタン32pxで44px基準未達、20→30回に10タップ | B-1 |
| 4. 個別化 | PT | 目的・頻度・注意メモ・並び替え | ▲▼が20pxと小さい／削除ボタンが孤立して作りかけに見える | B-2, B-3 |
| 5. 確認・出力 | PT | PDF生成 + 共有シート | 画面名「プレビュー」なのに完成形が見えない／3本バーの意味が不明／戻るたびに確認ダイアログ | B-4, B-5 |
| 6. 説明・実技指導 | PT→患者 | 紙（患者の前でアプリは使わない運用） | 指導直前にポイントを再確認する手段が薄い | A-2 が兼ねる |
| 7. 手渡し・共有 | PT→患者 | 印刷 / LINE / AirDrop / メール | **スマホWeb版で印刷画面が横破綻（実害バグ）** | B-6 |
| 8. 自宅での実施 | **患者** | 紙（イラスト+28pt処方数値+注意） | **継続の仕掛けがない（課題⑤）** | C-1 |
| 9. 再評価・調整 | PT | **なし** | 前回と同じメニューを毎回ゼロから組み直す | C-2 |

### 支援しないと決めていること（再確認、decisions.md 準拠）

- 運動の自動推奨・疾患タグ・症状入力（SaMD リスク）
- 動画・チャット・アプリ内トラッキング（競合の土俵。紙で完結が差別化）
- 患者データのクラウド送信・患者アカウント
- カスタム運動作成

## 4. 施策仕様

### A. 運動選定の再設計（ライブラリ画面） ✅ **バッチ2として実装完了**（2026-07-31, コミット 800f0c2）

**A-1. フィルタ再設計 + ヘッダー圧縮**（方式: 部位常設+絞り込みシート）
- ロゴ行とタイトル行を1行に統合（約50px回収）
- **部位（すべて/下肢/体幹/上肢）のみ常設**のセグメントコントロール。臨床では部位が第一の絞り込み軸であり、4択は1行に収まる
- 姿勢・種類は検索バー右の**「絞り込み」ボタン → ボトムシート**へ。シート内は全選択肢をグリッド表示（横スクロール廃止、「四つ這い」「呼吸」が必ず見える）
- 適用中の絞り込みはボタンにバッジ数 + リスト上部にチップ（×で個別解除）
- 実測: リスト開始位置 y≈780 → y≈180、初期表示の運動カード 3件 → 5件（選択トレイ表示時4件）

**A-2. 運動詳細モーダル**
- サムネイルタップで詳細モーダル: 大きいイラスト + 説明文 + 実施ポイント3つ + 選択トグル
- カード本体タップ=選択（現行維持）と役割分離
- フロー2（名前が曖昧な運動の確認）とフロー6（指導直前のポイント再確認）を1つのUIで支援
- phase6 の「運動カード詳細展開」はこの仕様で置き換えた（インライン展開よりリスト一覧性を守れる）
- サムネイル右下に `i` バッジを置いて、タップできることを示す

**A-3. 選択トレイ**
- CTA直上に「選択中: パテラセッティング、SLR…」の1行サマリ。タップでボトムシート展開
- シート内: 選択済み一覧（サムネ+名前+解除ボタン）、そのまま「指導書を作成」へ
- 10種選んだ後に「何を選んだっけ」を100件リストから探し直す問題を解消
- ⚠️ 実装知見: ボトムシートは `absolute` 背景 + `justify-end` + ScrollView `shrink` で組む。
  背景を `flex-1` にすると max-height の百分率が解決されずシートが画面外にはみ出す

### B. 調整・出力の磨き込み ✅ **バッチ1として実装完了**（2026-07-31, コミット d41d4b4）

- **B-1. ステッパー44px化 + 長押しオートリピート**（100ms間隔）。回数20→30が1タップ+長押しで完了
  - ⚠️ 実装知見: **RN Web の Pressable では `onPressIn` が発火しない**（同画面の `onPress` は動作する）。
    単発は `onPress`、連続は `onLongPress`（delay 500ms）→ `setInterval`、停止は `onPressOut` で実装。
    `onPressOut` が来ない環境での暴走防止に上限100回のガードを入れている。
  - ⚠️ 連続増減中は `useRef` で最新値を参照する（interval のクロージャが初期値を掴むため）
- **B-2. 並べ替え▲▼**: 見た目は現行、hitSlop で実効44pxを確保
- **B-3. 削除**: 展開部末尾に全幅の「この運動を外す」ボタン（warn-soft背景）。孤立✕を廃止
- **B-4. 画面名「内容を調整」+ ラベル付きステップ表示**（1.選ぶ / 2.調整 / 3.出力）。無説明の3本バーを置換
- **B-5. 戻る時の確認ダイアログ廃止**（選択は保持される。破壊的なのは「すべて解除」だけで、そちらの確認は維持）
- **B-6. Web印刷画面の修正**: `generateHtml` に `forScreen` フラグを追加し、**画面表示時のみ**
  viewport(A4幅 794/1123px) と `@media screen` の紙面スタイルを出力。expo-print の PDF 生成は不変。
  ツールバーの `#0EA5E9` を白/navy に修正。**Web版の最重要バグ**
  - 検証済み: モバイル幅で `scrollWidth === clientWidth`（横はみ出しなし）
  - 既知の制約: デスクトップで幅794px未満に縮めた場合のみ横スクロール（PDFビューア同等として許容）

**実装知見**
- 当初は「4種目まで4週1枚 / 5種目以上2週×2枚」の固定ルールだったが、向き別の係数
  （fixed / perWeek / rowH / memo / budget / columns）から高さを見積もる方式に変更した。
  **要素の高さを変えたら再較正が必要**。
- ⚠️ **最大の学び: 印刷可能高は A4 の理論値ではない**。ブラウザ印刷はURL・日付を付加するため
  実効値は縦約750px / 横約490px しかなかった（理論値は1047 / 718）。
  実機で「フッターだけが次ページに落ちる」症状から逆算して判明。budget は縦700 / 横480 に設定。
  詳細は DESIGN.md §7。
- ⚠️ 行の高さは `td { height }` ではなくセルの中身が決める（実測41.6px）。
  運動名と処方を2行→1行に統合して 31px → 21px にした。
- 検証結果（全ページ上限内・運動名の切れなし）:
  縦3種目 表紙576/表674 ・ 縦10種目 表紙698/表398×3・475 ・ 横3種目 表紙462/表439 ・ 横10種目 表紙617/表388・463

**C-2. テンプレート（Phase 3）の位置づけ再定義**
- 単なる「リピート効率化」ではなく**フロー9（再評価・調整）の支援機能**として設計する
- 「よく使う処方パターン」を名前を付けて保存 → 呼び出し → 患者に合わせ微調整 → 出力
- 患者名・患者IDは保存しない（個人情報最小化の維持）。保存するのはパターンのみ
- 実装仕様は tasks/phase3-templates.md のまま（expo-sqlite / iOS。Web は localStorage で追随可能だが後続判断）
